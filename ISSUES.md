# Найденные проблемы EvLamp

Документ составлен по результатам ревью ветки `code-review` (коммит `8a8ac0e`, совпадает с `master`).

- **Проект:** EvLamp, ESP-IDF v6.1-671-g9bf0c0eb952 (`release/v6.1`), поддерживаемые таргеты `esp32` и `esp32s3`.
- **Что просмотрено:** весь `main/` (≈2 600 строк), 32 эффекта (`main/effects/*.c`, ≈2 329 строк), `main/Kconfig.projbuild`, `files/web/index.html`, а также используемые компоненты из `managed_components/` (`esp-idf-lib__framebuffer`, `espressif__led_strip`, `esp-idf-lib__color`, `esp-idf-lib__lib8tion`).
- **Метод:** чтение кода, 4 параллельных прохода (эффекты; HTTP/API и веб; настройки/ядро/шина; ввод/Wi-Fi/палитры) с последующей перекрёстной проверкой ключевых находок по исходникам.
- **Проверка:** сборка обоих таргетов проходит; на реальном железе ничего из перечисленного не воспроизводилось. Численные оценки (индексы, underflow, OOB) проверены расчётом по коду.

## Легенда приоритетов

| Приоритет | Значение |
|---|---|
| **P0** | Паника, зависание задачи рендера, watchdog-ресет или полная потеря управления, достижимые в штатной эксплуатации. |
| **P1** | Ломает заявленную функцию, безопасность или конкретный пользовательский сценарий. |

# P0 — крэш, зависание, потеря управления

## EVL-001. Живая запись геометрии матрицы — выход за границы `blocks[]` и паника

- **Где:** `main/api.c:500-506` (запись), `main/api.c:452-461` (валидация), `main/surface.c:49-53` (использование), `main/api.c:127-130` (reset).
- **Суть:** обработчик `POST /api/settings/leds` валидирует новые `block_width`/`block_height`/`h_blocks`/`v_blocks`, после чего **немедленно** пишет их в `sys_settings.leds` и отвечает `"Settings saved, reboot to apply"`. При этом `blocks[]`, `num_blocks` и фреймбуфер уже зафиксированы в `surface_init()`.
- **Механизм:** `set_strip_pixel()` каждый кадр вычисляет индекс блока из живых полей:
  ```c
  size_t b = y / block_height * h_blocks + x / block_width;
  ```
  Если новые `h_blocks`/`v_blocks` больше фактически созданных, `b` выходит за `blocks[MAX_SURFACE_BLOCKS]`; если геометрия меняет разбиение иначе, `blocks[b].strip` может быть `NULL`. Обращение к `blocks[b].strip` в `led_strip_set_pixel()` даёт панику в задаче рендера.
- **Триггер:** валидный с точки зрения API запрос с другой геометрией, например `8×8` при `h_blocks=8`, или `GET /api/settings/reset` при геометрии, отличной от дефолтной (сбрасывает RAM-настройки без перезагрузки).
- **Исправление:** не менять живые поля до перезапуска: хранить «pending»-конфигурацию и применять её при старте, либо после сохранения выполнять `esp_restart()`. Правильнее — поддержать пересоздание surface (остановка задачи, освобождение strips/фреймбуфера, повторная инициализация), но это отдельная задача.
- **Проверка:** подтверждено чтением `api.c` и `surface.c`.

## EVL-002. Бесконечный цикл в эффекте `dna` при высоте матрицы ≥ 256

- **Где:** `main/effects/dna.c:59`.
- **Суть:** счётчик строк объявлен `uint8_t`, а высота — `size_t`:
  ```c
  for (uint8_t i = 0; i < fb->height; i++)
  ```
- **Механизм:** при `fb->height >= 256` (например `EL_MATRIX_HEIGHT=128`, `EL_MATRIX_V_BLOCKS=2`) после `i = 255` происходит переход в 0, условие никогда не становится ложным. Задача рендера крутится внутри эффекта, `fb_end()` не вызывается, семафор кадра не отдаётся.
- **Последствие:** зависание задачи рендера → срабатывание task watchdog → перезагрузка. Это не «плохая картинка», а гарантированный цикл перезагрузок при легальной конфигурации.
- **Исправление:** `for (size_t i = 0; i < fb->height; i++)`. Вспомогательные функции (`horizontal_line` и т.п.) при необходимости тоже перевести на `size_t`/`int`.
- **Проверка:** подтверждено чтением.

## EVL-003. Утечка мьютекса кадра в `gif.c` при ошибке декодирования

- **Где:** `main/effects/gif.c:149-157`.
- **Суть:** после успешного `fb_begin(fb)` при ошибке `nsgif_frame_decode()` выполняется `return ESP_FAIL` **без** `fb_end(fb)`.
- **Механизм:** `fb_begin()` делает `xSemaphoreTake(fb->mutex, 0)`, а `fb_end()` — единственное место, где семафор отдаётся. После ошибки декодирования (битый или неполный кадр, OOM внутри `nsgif`) мьютекс остаётся занятым до перезагрузки.
- **Последствие:** все последующие `fb_begin()`/`fb_render()` возвращают `ESP_ERR_INVALID_STATE` (таймаут 0, `framebuffer.c:81-82`, `235`), дисплей навсегда замирает на последнем кадре; в лог льётся только «Effect run error».
- **Исправление:** вызвать `fb_end(fb)` перед `return ESP_FAIL` либо перенести декодирование до `fb_begin()` (как сделано для `nsgif_frame_prepare()`).
- **Проверка:** подтверждено чтением.

## EVL-004. `fb_render()` не отдаёт мьютекс при ошибке рендер-колбэка

- **Где:** `managed_components/esp-idf-lib__framebuffer/framebuffer.c:83`.
- **Суть:** библиотека делает
  ```c
  CHECK(fb->render(fb, render_ctx));
  xSemaphoreGive(fb->mutex);
  ```
  то есть при ошибке колбэка мьютекс не освобождается.
- **Механизм:** наш `render_frame()` (`main/surface.c:67-77`) возвращает ошибку `led_strip_refresh()`. Достаточно одного сбоя RMT (занятая транзакция, ошибка `rmt_transmit`/`rmt_tx_wait_all_done`), чтобы framebuffer оказался заблокирован навсегда.
- **Последствие:** полная остановка вывода до перезагрузки, при этом внешне «всё работает» — эффекты считаются, но не рисуются.
- **Исправление:** патчить managed-компонент нельзя (перезаписывается), поэтому практичный вариант — не возвращать ошибку из `render_frame()` наружу: логировать сбой `led_strip_refresh()` и продолжать. Дополнительно можно перейти на собственную обёртку framebuffer либо зафиксировать версию компонента в `dependencies.lock` и патчить её через `override_path`.
- **Проверка:** подтверждено чтением `framebuffer.c` и `led_strip_rmt_dev.c:139-151`.

## EVL-005. `settings_init()` возвращает ошибку после успешного восстановления NVS — паника при старте

- **Где:** `main/settings.c:129`, `main/main.c:99`.
- **Суть:** при `nvs_flash_init()` с `ESP_ERR_NVS_NO_FREE_PAGES` или `ESP_ERR_NVS_NEW_VERSION_FOUND` выполняется `nvs_flash_erase()`, повторная инициализация и сброс настроек, но функция возвращает **исходный** `res`.
- **Последствие:** `ESP_ERROR_CHECK(settings_init())` в `app_main()` аварийно завершает программу, хотя NVS уже восстановлена и устройство могло бы работать с дефолтами.
- **Исправление:** после успешного erase/re-init вернуть `ESP_OK`; исходный код ошибки только логировать.
- **Проверка:** подтверждено чтением.

## EVL-006. Boot loop на ESP32-S3 с дефолтными настройками кнопок

- **Где:** `main/Kconfig.projbuild:210-228`, `main/main.c:113`, `components/soc/esp32s3/include/soc/soc_caps.h:193`.
- **Суть:** пины кнопок по умолчанию — 25, 26, 27 и 0. На ESP32-S3 GPIO22-25 отсутствуют:
  ```
  SOC_GPIO_VALID_GPIO_MASK (0x1FFFFFFFFFFFFULL & ~(0ULL | BIT22 | BIT23 | BIT24 | BIT25))
  ```
- **Механизм:** `button_create()` для невалидного пина возвращает `ESP_ERR_INVALID_ARG`; `input_init()` пробрасывает ошибку, `ESP_ERROR_CHECK(input_init())` в `app_main()` вызывает панику → перезагрузка → повтор.
- **Последствие:** ESP32-S3 с настройками по умолчанию не запускается вообще, хотя таргет официально поддерживается.
- **Дополнительно:** матричные GPIO по умолчанию (5, 17, 16, 4, 2, 15, 22, 23) тоже содержат 22/23 — при `>6` блоках на S3 будет та же проблема.
- **Исправление:** задать разные значения по умолчанию через `depends on IDF_TARGET` / `default ... if IDF_TARGET_ESP32S3`, либо в `input_init()`/`surface_init()` трактовать невалидный пин как предупреждение, а не fatal. Валидацию пинов по `SOC_GPIO_VALID_GPIO_MASK` добавить в Kconfig невозможно — только в коде.
- **Проверка:** подтверждено чтением `soc_caps.h`, `main.c`, `input.c`.

# P1 — ломает функцию или безопасность

## EVL-007. `authmode` точки доступа не выводится из пароля

- **Где:** `main/wifi.c:139`; дефолт — `WIFI_AUTH_OPEN` в `main/settings.c`.
- **Суть:** при подъёме AP `authmode` берётся из NVS как есть. API (`main/api.c`) сохраняет пароль и `authmode` независимо.
- **Последствие:**
  - пароль задан через API, но `authmode` остался `WIFI_AUTH_OPEN` → точка доступа **открыта**, хотя пользователь задал пароль;
  - пароль пустой, а в NVS `WPA2` → `esp_wifi_set_config()` возвращает `ESP_ERR_WIFI_PASSWORD`, AP не поднимается, веб-интерфейс недоступен.
- **Исправление:** при инициализации вычислять `authmode` из длины пароля (`0` → `WIFI_AUTH_OPEN`, `>= 8` → `WIFI_AUTH_WPA2_PSK`), не хранить его отдельно как независимый параметр.
- **Проверка:** подтверждено чтением.

## EVL-008. Сохранение LED-настроек из веб-интерфейса всегда отклоняется

- **Где:** `main/api.c:435-441`, `files/web/index.html:536`.
- **Суть:** API требует поле `rotation` числом, а веб-интерфейс отправляет его закомментированным.
- **Последствие:** `POST /api/settings/leds` из UI всегда возвращает «Field `rotation` not found or invalid»; изменить геометрию/тип ленты через штатный интерфейс невозможно.
- **Исправление:** сделать `rotation` необязательным (при отсутствии — сохранять текущее значение) либо раскомментировать поле в `index.html`.
- **Проверка:** подтверждено чтением API и шаблона.

## EVL-009. Пустой пароль AP сохраняется при `WPA2` — AP не стартует

- **Где:** `main/api.c:309-316`.
- **Суть:** для точки доступа проверяется только верхняя граница длины пароля; пустая строка проходит валидацию при `authmode = WPA2`.
- **Последствие:** настройки сохраняются, после перезагрузки `esp_wifi_set_config()` завершается ошибкой `ESP_ERR_WIFI_PASSWORD`, AP не поднимается, устройство недоступно по сети.
- **Исправление:** при `WPA2` требовать минимум 8 символов либо при пустом пароле принудительно переключать `authmode` в `WIFI_AUTH_OPEN` (см. EVL-007).
- **Проверка:** подтверждено чтением.

## EVL-010. Нет аутентификации; пароли Wi-Fi отдаются по GET; CORS открыт всем

- **Где:** `main/api.c:11-12`, `main/api.c:149-163`.
- **Суть:** HTTP-сервер не требует никакой аутентификации, `GET /api/settings/wifi` возвращает сохранённые SSID и пароль, все ответы содержат `Access-Control-Allow-Origin: *`.
- **Последствие:** любой, кто находится в той же сети (в режиме AP — любой подключившийся, включая открытую точку доступа), может прочитать пароли, переконфигурировать устройство, перезагрузить его, а через CSRF-сценарии (EVL-019) — сделать это с чужого сайта.
- **Исправление:** как минимум не возвращать пароль в GET (отдавать маску), ограничить CORS конкретным origin/убрать, добавить токен (`X-Api-Key`) или basic-auth. Решение о модели безопасности — за владельцем проекта.
- **Проверка:** подтверждено чтением.

## EVL-011. Гонка `surface_pause()`/`surface_stop()` — анимация может замереть при смене эффекта

- **Где:** `main/surface.c:258` (`surface_pause`), `main/surface.c:269` (`fb_begin` в `surface_stop`), `main/surface.c:295-305` (`surface_set_effect`).
- **Суть:** пауза реализована как `vTaskDelay(FRAME_TICKS + 1)` — «подождать чуть дольше кадра», а не как ожидание фактического завершения кадра.
- **Механизм:** если эффект рисует дольше расчётного кадра (тяжёлый эффект, крупная матрица, конкурентная нагрузка), `surface_stop()` вызывает `fb_begin()` с таймаутом 0 и получает `ESP_ERR_INVALID_STATE`. `surface_set_effect()` выходит по `CHECK` **до** `surface_play()`, поэтому бит `BIT_PLAYING` снимается и не возвращается.
- **Последствие:** дисплей замирает на последнем кадре до следующего успешного переключения; в лог пишется ошибка эффекта.
- **Исправление:** синхронизировать паузу с задачей рендера (event group/семафор «кадр завершён», подтверждение остановки с таймаутом), а `surface_set_effect()` при ошибке `prepare` — откатываться к `surface_play()`.
- **Проверка:** подтверждено чтением.

## EVL-012. Чтение за границей массива палитры в эффекте `tunnel`

- **Где:** `main/effects/tunnel.c:58`, массив `pal[16]` — `main/effects/tunnel.c:24-28`.
- **Суть:** индекс считается как
  ```c
  c = 9 - y / 3 - ((0x2 >> (-y % 3)) & 1);
  ```
  В ветке с отрицательным `y` и большим `q - t` значение `c` растёт как `9 + |y|/3`.
- **Механизм:** `y` начинается с `-half_height - half_height/8`. При высоте 128 (`half_height = 64`) `y` доходит до −72, `c` — до 33, а массив содержит 16 элементов. `*pixel-- = rgb_from_code(pal[c])` читает до ~70 байт за пределы статического массива.
- **Численная проверка:** для `8×128` при `t = 0` 255 из 1024 пикселей имеют `c >= 16` (максимум 33); для `8×64` — 75 из 512. На дефолтных `16×16` максимум равен 15, поэтому на «столе» баг не виден.
- **Последствие:** OOB read из `.rodata` — мусорные цвета, формально неопределённое поведение; при неудачном размещении данных возможен fault.
- **Исправление:** клиппить индекс в `0..15` (`constrain`) либо переписать формулу на беззнаковую арифметику.
- **Проверка:** подтверждено расчётом.

## EVL-013. Деление на ноль и отрицательный делитель в эффекте `peacock`

- **Где:** `main/effects/peacock.c:24`; диапазон параметра — `1..255` (`main/effects/peacock.c:15`).
- **Суть:**
  ```c
  float t = (float)(esp_timer_get_time() / 1000) / (1000.0f - PARAM_VAL(peacock, P_SPEED) * 4);
  ```
- **Механизм:** при `P_SPEED = 250` знаменатель ровно `0.0f` → `t = +inf`; при `251..255` знаменатель отрицательный, `t` уходит в большие отрицательные значения. Дальше `sin8(x * P_SCALE + t * 6)` — преобразование `float` вне диапазона `uint8_t`, то есть UB на каждом пикселе.
- **Последствие:** параметр на своём разрешённом максимуме гарантированно ломает эффект (мусор/залипание/возможный fault).
- **Исправление:** ограничить `max` значением 249 либо защитить делитель (`if (d == 0) d = 1;` и не допускать отрицательного значения).
- **Проверка:** подтверждено чтением.

## EVL-014. Underflow `size_t` в `gif.c` — эффект полностью чёрный на матрицах меньше гифки

- **Где:** `main/effects/gif.c:116-117`, использование — `main/effects/gif.c:170`.
- **Суть:**
  ```c
  pos_x = fb->width / 2 - gif_info->width / 2;
  pos_y = fb->height / 2 - gif_info->height / 2;
  ```
  Оба операнда беззнаковые.
- **Механизм:** если гифка больше матрицы, результат — `SIZE_MAX - k`. Далее `fb_set_pixel_rgb(fb, pos_x + x, ...)` отбраковывается по границам.
- **Последствие:** эффект не рисует **ничего**. Все встроенные гифки 16×16, поэтому на конфигурациях 8×8…15×15 (минимум по Kconfig — 8) эффект всегда чёрный; замена гифки на 32×32 ломает его и на 16×16.
- **Исправление:** считать смещение в `int`/`int32_t` и клиппить прямоугольник вывода по границам фреймбуфера.
- **Проверка:** подтверждено расчётом и чтением.

# P2 — дефекты в краевых и допустимых сценариях

## HTTP/API и веб

### EVL-015. Тело HTTP-запроса читается одним `recv` без цикла
- **Где:** `main/api.c:80-87`.
- **Суть:** `httpd_req_recv(req, buf, req->content_len)` вызывается один раз; частичное чтение не обрабатывается.
- **Последствие:** `ESP_FAIL` и невычитанный остаток тела; на keep-alive соединении следующий запрос разбирается со сдвигом.
- **Исправление:** цикл до `content_len` с проверкой `HTTPD_SOCK_ERR_TIMEOUT`.

### EVL-016. Параметры эффекта применяются по одному
- **Где:** `main/api.c:740-755`.
- **Суть:** для каждого параметра отдельно вызывается `effect_param_set()`, а `surface` дёргается `pause`/`prepare`/`play` на каждый параметр.
- **Последствие:** промежуточные состояния (параметры применены частично), десятки лишних остановок рендера; при ошибке на середине — частично применённый набор.
- **Исправление:** валидировать весь массив, затем применять одной транзакцией; перезапуск surface — один раз.

### EVL-017. Приведение к `uint8_t`/`uint32_t` до проверки диапазона
- **Где:** `main/api.c:287, 302, 483, 492`.
- **Суть:** значения из JSON кастуются, и только потом проверяются границы.
- **Последствие:** `mode = 258` превращается в `2` (AP), `channel = 288` → `32`, `type = 259` → `WS2812`, отрицательный `limit` → `4294967295`.
- **Исправление:** проверять `cJSON`-значение как `int`/`double` в широком типе, кастовать после проверки.

### EVL-018. `brightness`/`fps` безусловно включают лампу
- **Где:** `main/api.c:654-671`.
- **Суть:** обработчик вызывает `surface_play()` независимо от поля `on`; `on` обрабатывается раньше `brightness` (порядок проверен).
- **Последствие:** `{"on": false, "brightness": 10}` в итоге оставляет лампу включённой.
- **Исправление:** включать рендер только при `on == true` либо не менять состояние `on` в этих обработчиках.

### EVL-019. GET-эндпоинты меняют состояние; нет проверки `Content-Type` — CSRF
- **Где:** `main/api.c` (`/api/settings/reset`, `/api/reboot`), общий разбор запросов.
- **Суть:** сброс настроек и перезагрузка доступны через GET, тело POST разбирается без проверки типа содержимого.
- **Последствие:** смена состояния и перезагрузка по ссылке/картинке с любого сайта; вместе с EVL-010 — полный контроль над устройством из браузера жертвы.
- **Исправление:** только POST/DELETE с проверкой `Content-Type: application/json`, CSRF-токен или `X-Api-Key`.

### EVL-020. Висячий указатель `server` после неудачного `httpd_start`
- **Где:** `main/webserver.c:46-61`.
- **Суть:** `server` не обнуляется после `httpd_stop()`; при ошибке `httpd_start()` остаётся ненулевой указатель на уже освобождённый сервер.
- **Последствие:** use-after-free при следующем `EVENT_NETWORK_UP` (повторный `httpd_stop`/`httpd_start`).
- **Исправление:** `server = NULL` сразу после `httpd_stop()` и при ошибке старта.

## Ядро, шина, настройки

### EVL-021. Блокирующая отправка в шину из колбэка кнопок
- **Где:** `main/input.c:16`, `main/bus.c:31`.
- **Суть:** колбэк кнопок выполняется в задаче `esp_timer`, а `bus_send_event()` делает `xQueueSend(..., pdMS_TO_TICKS(BUS_TIMEOUT_MS))` — до 500 мс.
- **Последствие:** блокировка системного таймера и обработки других кнопок; результат отправки игнорируется.
- **Исправление:** для событий кнопок использовать неблокирующую отправку (таймаут 0) и отдельную очередь/задачу, либо переносить обработку из таймера.

### EVL-022. Результаты `bus_send_event` не проверяются
- **Где:** `main/bus.c:18` и вызовы.
- **Суть:** ошибка `xQueueSend` игнорируется.
- **Последствие:** потеря `EVENT_NETWORK_UP` оставляет устройство без HTTP-сервера до перезагрузки; потеря событий кнопок — «залипшие» действия.
- **Исправление:** логировать ошибки и, для критичных событий, иметь повтор/флаг состояния.

### EVL-023. Нет версии раскладки настроек; сброс поверх Wi-Fi кредов
- **Где:** `main/settings.c:67-84`.
- **Суть:** при несовпадении размера blob настройки сбрасываются целиком; копирование выполняется до проверки размера.
- **Последствие:** после обновления прошивки с изменённой структурой теряются Wi-Fi-креды и все настройки; при частичном чтении возможно копирование мусора.
- **Исправление:** версия/магия + миграция полей; проверка размера до `memcpy`.

### EVL-024. Утечка хендла NVS в `storage_save`
- **Где:** `main/settings.c:104-110`.
- **Суть:** `CHECK_LOGE` завершает функцию до `nvs_close()`.
- **Последствие:** утечка хендла при каждой неудачной записи; при частых ошибках — исчерпание ресурса.
- **Исправление:** единая точка выхода с `nvs_close()` (goto cleanup).

### EVL-025. `sys_settings_reset()` мутирует `sys_defaults`
- **Где:** `main/settings.c:139`.
- **Суть:** сброс присваивает/меняет поля в неконстантном `sys_defaults` (в частности `authmode`).
- **Последствие:** «дефолты» перестают быть дефолтами после первого сброса; повторный сброс даёт другое состояние.
- **Исправление:** `const` для `sys_defaults` и копирование в рабочую структуру.

### EVL-026. Загруженные из NVS значения не валидируются
- **Где:** `main/settings.c` (загрузка), `main/surface.c:9` (`FRAME_TICKS`), `main/surface.c:188`.
- **Суть:** после чтения blob значения (fps, яркость, геометрия, тип ленты, поворот) не проверяются.
- **Последствие:** `fps == 0` → деление на ноль в `FRAME_TICKS` и boot loop; `block_width/height` до 255 → падение аллокации в `led_strip`; невалидный `type` — ошибка инициализации.
- **Исправление:** валидировать каждое поле после загрузки и при невалидном значении откатываться к дефолту с логом.

### EVL-027. Нет гарантии NUL-терминации строк из NVS
- **Где:** `main/settings.c:79`, `main/wifi.c:136, 144, 177`.
- **Суть:** `ssid[32]`/`password[64]` заполняются из blob/копируются, затем используются в `strlen`/`%s`.
- **Последствие:** чтение за границей массива, мусор в логах, неверная длина при настройке Wi-Fi.
- **Исправление:** принудительно ставить `'\0'` в последний элемент после чтения/копирования; проверять длину.

### EVL-028. Статический IP применяется после подключения к STA поверх DHCP
- **Где:** `main/wifi.c:87`.
- **Суть:** `esp_netif_set_ip_info`/остановка DHCP-клиента выполняются в обработчике `STA_CONNECTED`, после того как DHCP уже мог выдать адрес.
- **Последствие:** событие `LOST_IP` → переподключение, возможны мигающие адреса и таймауты.
- **Исправление:** останавливать DHCP-клиент до `esp_wifi_connect()` (или на этапе инициализации netif при статическом конфиге).

### EVL-029. Переподключение без backoff
- **Где:** `main/wifi.c:89-94`.
- **Суть:** при `DISCONNECTED` сразу вызывается `esp_wifi_connect()`.
- **Последствие:** при неверном пароле/отсутствии AP — плотный цикл попыток, нагрузка на RF и логи.
- **Исправление:** экспоненциальная задержка с верхним пределом, сброс после успешного подключения.

### EVL-030. Канал AP 14..32 проходит валидацию, но softAP его не принимает
- **Где:** `main/wifi.c:140`, `main/api.c:302-303`.
- **Суть:** диапазон проверяется как 1..32, тогда как softAP поддерживает 1..13 (для 2.4 ГГц).
- **Последствие:** `esp_wifi_set_config` возвращает ошибку, AP не поднимается.
- **Исправление:** ограничить канал 1..13 (или 1..11 для некоторых регионов) на уровне API.

### EVL-031. Kconfig не проверяет валидность и пересечения GPIO
- **Где:** `main/Kconfig.projbuild` (матрица и кнопки).
- **Суть:** диапазон `0..39` включает input-only 34-39 на ESP32 и отсутствующие на S3 пины; пересечения пинов матрицы и кнопок не проверяются.
- **Последствие:** непонятная ошибка инициализации или «мёртвая» кнопка/строка матрицы; на S3 — boot loop (см. EVL-006).
- **Исправление:** проверка в коде на этапе инициализации с внятным логом; для S3 — список допустимых пинов.

### EVL-032. `surface_init` не проверяет размер блока против `MAX_BLOCK_LEDS`
- **Где:** `main/surface.c:188`; проверка в API — `main/api.c:460`.
- **Суть:** `strip_len = block_width * block_height` не сверяется с `MAX_BLOCK_LEDS` (1024), хотя Kconfig допускает `128×128 = 16384`.
- **Последствие:** аллокация пиксельного буфера в `led_strip` падает; в `surface_task` стоит `ESP_ERROR_CHECK` (`main/surface.c:139`) → цикл перезагрузок. Через NVS (EVL-026) это достижимо без API.
- **Исправление:** проверять `strip_len` в `surface_init` до создания strip и отказывать с логом/дефолтом. (Ранее в переписке я ошибочно сказал, что `MAX_BLOCK_LEDS` не используется — он используется в `api.c:460`, но не в `surface_init`.)

### EVL-033. Поворот матрицы не реализован
- **Где:** `main/surface.c:48` (`// TODO: support rotation`), `main/surface.c:194-198` (закомментированный блок), `main/surface.c:199-200` (размеры фреймбуфера), `main/surface.c:53` (snake-маппинг).
- **Суть:** `sys_settings.leds.rotation` сохраняется и отдаётся по API, но нигде не применяется: ни к размерам фреймбуфера, ни к маппингу пикселей.
- **Последствие:** настройка поворота не работает; для матриц с нестандартной ориентацией картинка повёрнута.
- **Исправление:** реализовать преобразование координат (0/90/180/270) при записи пикселя и соответствующий swap `width/height` при `90/270`, либо убрать настройку из API/UI до реализации.

### EVL-034. Индекс эффекта не проверяется в цикле рендера
- **Где:** `main/surface.c:158`.
- **Суть:** `effects[vol_settings.effect]` читается каждый кадр без проверки границ; клампинг есть только в `surface_init` (`main/surface.c:230-231`).
- **Последствие:** при изменении `vol_settings.effect` из другой задачи/из NVS без клампинга — OOB по массиву указателей.
- **Исправление:** клампить/валидировать при каждой установке значения (в API/настройках), в цикле использовать проверенную локальную копию.

### EVL-035. Утечки при ошибках в `surface_init`
- **Где:** `main/surface.c:182-186`, `main/surface.c:220-225`.
- **Суть:** при `num_blocks > MAX_SURFACE_BLOCKS` и при сбое `xTaskCreate` не освобождается event group.
- **Последствие:** утечка при повторной инициализации; в текущем коде инициализация однократная, поэтому риск низкий.
- **Исправление:** единый cleanup-путь.

### EVL-036. Двойное масштабирование яркости
- **Где:** `main/surface.c:72-73`.
- **Суть:** `rgb_scale_video(rgb_scale_video(pixel, vol_settings.brightness), strip_brightness)` — два последовательных `scale8_video`.

- **Исправление:** если нужна точная эквивалентность — считать произведение коэффициентов и применять один раз; если важна плавность — задокументировать поведение.

## Эффекты

### EVL-037. `sun`: bump-map пишется и читается с разными шагами
- **Где:** `main/effects/sun.c:42`, `main/effects/sun.c:51-61`.
- **Суть:** `generate_bump()` обходит `x` внешним циклом и пишет `bump_map[i++]` (фактический шаг `height+2`), а `run()` адресует `bump_map[x + idx_y ± 1]` и `± (fb->width + 2)` (шаг `width+2`).
- **Последствие:** на неквадратной матрице (например 128×32) `nx`/`ny` считаются по несвязанным парам байт — «солнце» превращается в шум. Индексы остаются в пределах выделенного `(w+2)*(h+2)` (максимум = размер−2), порчи памяти нет.
- **Исправление:** в `generate_bump` писать `bump_map[y * (fb->width + 2) + x]`.

### EVL-038. `fire`: `abs8()` режет вертикальный градиент при высоте > 128
- **Где:** `main/effects/fire.c:48`.
- **Суть:** `abs8(y - (fb->height - 1)) * 255 / (fb->height - 1)`, где `abs8` принимает `int8_t`, а `y` — `size_t`.
- **Последствие:** при `h = 256`, `y = 10` вместо 245 получается 11; при `h = 1024` — 6. Градиент затухания к верху пропадает/инвертируется; при `h >= 129` возможен `abs8(-128)`.
- **Исправление:** `(uint8_t)((fb->height - 1 - y) * 255 / (fb->height - 1))` без `abs8`.

### EVL-039. `holiday`: строки берутся из ширины; неинициализированная `c`; усечение `random8_between`
- **Где:** `main/effects/holiday.c:26, 38, 50, 64`; `main/effects/holiday.c:52-55`.
- **Суть:** циклы `for (int i = 0; i < fb->width - 1; i++)`, но `i` используется как координата `Y` в `fb_set_pixelf_hsv(fb, fx / 10, i, ...)`. Далее `rgb_t c;` не инициализирована, `fb_get_pixel_rgb()` при `i >= height` возвращает ошибку и не трогает `c`, после чего читается `rgb_is_zero(c)`. Аргументы `random8_between(i * 2, (fb->width - 1) * 4 - i * 2)` — `uint8_t`.
- **Последствие:** на 128×8 рисуются только 8 строк, остальные 119 итераций отбрасываются, причём `x` прижат к левому краю (эффект почти пустой); на 8×128 — 7 строк из 128. При `width = 128`, `i = 100` минимум 200, максимум 308→52, диапазон вывернут, `fx` уезжает за ширину. `rgb_is_zero(c)` читает мусор со стека (UB).
- **Исправление:** цикл по `fb->height`, отдельный счётчик для `x`; `rgb_t c = {0}` и проверка кода возврата `fb_get_pixel_rgb`; `fx` считать в `int`/`uint16_t` с клиппингом.

### EVL-040. `hoop`: `256 / width` даёт мёртвые столбцы
- **Где:** `main/effects/hoop.c:29-35`.
- **Суть:** `uint8_t div_x = 256 / fb->width;` (и `div_y`), затем `sin8(...) / div_x`.
- **Последствие:** при `width = 300` делитель 0 → принудительно 1, столбцы 256..299 не зажигаются никогда; при `width`, не делящей 256 (например 100 → `div_x = 2`, максимум 127), часть пикселей с `x >= 100` отбрасывается — «полосы». Для 8/16/32 работает только потому, что 256 делится на степень двойки.
- **Исправление:** `x = sin8(...) * fb->width / 256` вместо деления.

### EVL-041. `lava`: палитра из 7 элементов, индекс 7 читается за границей
- **Где:** `main/effects/lava.c:64`, палитра — `main/effects/lava.c:28-36`; библиотека — `managed_components/esp-idf-lib__color/color.c:889`.
- **Суть:** `color_from_palette_rgb(lava_palette, LAVA_PALETTE_SIZE, noise, 255, true)`; внутри `div = 256 / pal_size` (для 7 → 36), `hi = index / div`; при `noise = 252..255` получается `hi = 7`.
- **Последствие:** чтение `palette[7]` за концом массива — ~1.6 % пикселей в режиме `LAVA` берут цвет из соседних `.rodata` (визуально случайные вспышки), формально OOB read.
- **Исправление:** добавить 8-й элемент, клиппить индекс (`MIN(noise, 251)`) или передавать размер, кратный степени двойки.

### EVL-042. Палитра `p_heat` из 13 цветов, индекс 13 читается за границей
- **Где:** `main/palettes.c:26`; та же библиотечная формула `color.c:889`.
- **Суть:** `div = 256 / 13 = 19`, при `index >= 247` получается `hi = 13`, то есть `p_heat[13]`.
- **Последствие:** OOB read; достижимо из эффектов, подающих «сырой» индекс 0..255 с любой палитрой: `lava.c:67-68` (`P_PALETTE`) и `dunes.c:40-43` (`pixel_hue >> 8`) при выбранной `PALETTE_HEAT`.
- **Исправление:** дополнить `p_heat` до 16 элементов либо клиппить `hi` к `pal_size - 1` (потребует локальной копии/патча `color`).

### EVL-043. `gif`: висячий указатель при неудачном `nsgif_create`
- **Где:** `main/effects/gif.c:91-99`, проверка — `main/effects/gif.c:126`.
- **Суть:** после `nsgif_destroy(gif)` указатель не обнуляется; `nsgif_create()` пишет в `*gif_out` только при успехе.
- **Последствие:** при `NSGIF_ERR_OOM` глобальный `gif` указывает на освобождённый объект, а `effect_gif_run()` проверяет лишь `if (!gif)` → use-after-free на следующем кадре.
- **Исправление:** `gif = NULL;` сразу после `nsgif_destroy(gif)`.

### EVL-044. `octopus`: отказ `prepare` на нечётных размерах оставляет анимацию остановленной
- **Где:** `main/effects/octopus.c:40-43`, `main/surface.c:295-302`.
- **Суть:** `prepare()` возвращает `ESP_FAIL`, если `fb->width % 2 || fb->height % 2`. Kconfig допускает нечётные значения (например 15).
- **Последствие:** `surface_set_effect()` уже выполнил `surface_stop()`, затем выходит по `CHECK(prepare)` — `surface_play()` не вызывается, `BIT_PLAYING` остаётся снятым, дисплей стоит на последнем кадре (лечится только переключением эффекта). Плюс `map` не очищается.
- **Исправление:** обрабатывать нечётные размеры (центр `width/2`, последний столбец/строка как есть) либо откатывать `surface_play()` при ошибке `prepare`.

### EVL-045. `spaceships`: направление может стать −1 и застрять
- **Где:** `main/effects/spaceships.c:87`.
- **Суть:** `dir += random8_to(2) ? 1 : -1; if (dir >= DIR_MAX) dir = DIR_UP;` — проверяется только верхняя граница.
- **Последствие:** из `DIR_UP` (0) при выпадении −1 получается −1, условие ложно, `switch` уходит в `default` — `fb_shift` не вызывается, корабли копятся/размазываются на месте, пока случайно не выпадет +1.
- **Исправление:** нормализовать `dir` по модулю `DIR_MAX` или добавить `if (dir < 0) dir = DIR_MAX - 1;`.

### EVL-046. `rain`: отрицательный масштаб превращается в 206..255
- **Где:** `main/effects/rain.c:43`; `rgb_scale()` — `managed_components/esp-idf-lib__color/rgb.h:168` (принимает `uint8_t`).
- **Суть:** `PARAM_VAL(rain, P_TAIL) + random8_to(100) - 50` при `P_TAIL = 100` и `random < 50` даёт −49..−1.
- **Последствие:** приведение к `uint8_t` даёт 207..255 — вместо затухания хвоста почти полная яркость, случайные яркие вспышки на верхней строке.
- **Исправление:** считать в `int` и клиппить к 0, либо перенести −50 внутрь параметра.

### EVL-047. `waterfall`: размер `map` фиксируется навсегда
- **Где:** `main/effects/waterfall.c:53`, макрос `MAP_XY` — `main/effects/waterfall.c:81`.
- **Суть:** `if (!map) map = calloc(fb->width * fb->height, 1);` — размер привязан к размерам на момент первого `prepare`, буфер никогда не освобождается/не перевыделяется.
- **Последствие:** пока `fb_width/fb_height` не меняются в рантайме — «вечная» утечка одного буфера. При будущем пересоздании фреймбуфера (смена конфигурации без ресета, повторный `fb_init`) `map` останется маленьким, и `MAP_XY(x, y)` начнёт писать за его границы — порча кучи.
- **Исправление:** хранить `map_size` и при несовпадении `free()` + `calloc()`; либо выделять буфер в `fb->internal`.

# Системная непереносимость эффектов на «блочные» размеры

Общий корень: координаты, границы `beatsin8`/`random8_to` и счётчики строк хранятся в `uint8_t`/`int8_t`, тогда как Kconfig с блоками допускает до 1024 пикселей по стороне. Запись идёт через `fb_set_pixel_*`, которые проверяют границы, поэтому память почти нигде не портится — но картинка ломается: эффект рисует в углу, заворачивается или полностью пустой.

### EVL-048. `random8_to(fb->width)` при ширине ≥ 256
- **Где:** `main/effects/crazybees.c:34-35, 44-45`, `main/effects/whirls.c:35`, `main/effects/metaballs.c:72-73`, `main/effects/spaceships.c:79-80`, `main/effects/dna.c:61-64`, `main/effects/matrix.c:37`.
- **Суть:** `uint8_t random8_to(uint8_t lim)` считает `(random8() * lim) >> 8`, поэтому `fb->width` усекается по модулю 256.
- **Последствие:** при `width = 512` `lim = 0` и все объекты оказываются в столбце 0; при `width = 300` — в полосе 0..43. `matrix.c:37` (`random8_to(7 * fb->height)`) при `height = 256` даёт 0 — хвост схлопывается мгновенно.
- **Исправление:** `random16_to()`/`random16()` и `size_t`/`uint16_t` для координат.

### EVL-049. `beatsin8` с `highest = fb->width - 1`
- **Где:** `main/effects/rays.c:62-65`.
- **Суть:** `highest` имеет тип `uint8_t`; при `width = 260` значение 259 усекается до 3, и диапазон выворачивается (`highest < lowest`).
- **Последствие:** луч рисуется в узкой полосе/некорректно.
- **Исправление:** `beatsin16()` и широкий тип.

### EVL-050. Координаты и `y` в `uint8_t` в `twister`
- **Где:** `main/effects/twister.c:29, 61-64`.
- **Суть:** `uint8_t x1..x4`, `x1 = sin8(...) * fb->width / 255`, затем `x1 = x1 >= fb->width ? fb->width - 1 : x1;`.
- **Последствие:** при `width = 1024` значение (до 1024) усекается до 0..255, а clamp не срабатывает, потому что `uint8_t` не может быть `>= 1024`: картинка занимает левую четверть и заворачивается. `y` в `horizontal_line` тоже `uint8_t` — при `height > 255` строки повторяются.
- **Исправление:** считать в `uint16_t`/`size_t` с клиппингом, `y` принимать как `size_t`.

### EVL-051. Геометрия `tunnel` в `uint8_t`/`int8_t`
- **Где:** `main/effects/tunnel.c:20-21, 32-33, 46-48`.
- **Суть:** `static uint8_t half_width`, `half_height`; цикл `for (int8_t y = -half_height - half_height / 8; ...)`.
- **Последствие:** при `width = 512` `half_width = 0` (512/2 = 256 → 0) и цикл не выполняется; при `height = 256` то же. При `half_height >= 113` начальное значение выходит за `int8_t` и заворачивается в положительное, условие цикла сразу ложно — туннель чёрный. Переполнения буфера нет: запись ограничена `2*half_*`.
- **Исправление:** `size_t half_width/half_height`, `int y`.

### EVL-052. Общий вывод по эффектам
- Все перечисленные случаи — одна системная проблема, а не независимые баги: типы координат и границ не соответствуют допустимому диапазону размеров (`8..1024` на сторону).
- Рекомендуется отдельный проход: перевести координаты/индексы на `size_t`/`uint16_t`, заменить `random8_to`/`beatsin8` на 16-битные варианты, добавить клиппинг прямоугольников вывода.
- После этого имеет смысл добавить сборку/тест-рендер хотя бы для `8×8`, `16×16`, `128×32`, `64×256`, чтобы такие дефекты ловились автоматически.

# Известные ограничения анализа

1. **Железо не проверялось.** Тайминги RMT, поведение кнопок на S3, реальные проявления гонки кадра и OOB-чтений требуют стенда.
2. **Managed-компоненты не патчились.** Находки в `framebuffer`/`color` (EVL-004, EVL-041, EVL-042) требуют решения: локальная обёртка, фиксация версии с `override_path` или отказ от компонента.
3. **Не является багом:** `CONFIG_ESPTOOLPY_FLASHMODE` строкой `"dio"` при `CONFIG_ESPTOOLPY_FLASHMODE_QIO=y` — в IDF 6.1 esptool прошивает в DIO, загрузчик переключается на QIO. Так задумано.
4. **Ранее исправленное утверждение:** `MAX_BLOCK_LEDS` действительно используется — в `main/api.c:460`; проблема не в отсутствии проверки в API, а в отсутствии её в `surface_init` (EVL-032) и в возможности обойти API через NVS (EVL-026).
5. **Приоритеты расставлены по достижимости и последствиям**, а не по объёму правки: EVL-001…006 дают панику/зависание/потерю управления в обычной работе, EVL-007…014 ломают конкретные пользовательские сценарии.
